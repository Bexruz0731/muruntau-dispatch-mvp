# MVP: диспетчеризация карьерных самосвалов Мурунтау + ИИ-ассистент по документации

Дата: 2026-08-11
Статус: утверждено (ожидает финального ревью пользователем)

## Контекст и цель

Демо для хакатона: веб-приложение из трёх экранов.
1. 3D-карта карьера с живой симуляцией GPS-трекеров самосвалов, алгоритмом диспетчеризации, синхронизацией топлива и детектом аномалий/неисправностей (всё — чистая математика, без LLM), с возможностью попросить LLM объяснить решение диспетчера или причину аномалии человеческим языком.
2. Отдельная вкладка "Полный отчёт по топливу" — сессионная таблица по всем машинам с AI-сводкой одним абзацем (единственное уместное применение LLM здесь — суммаризация текста, не расчёт).
3. Чат с ИИ-ассистентом по технической документации через локальный AnythingLLM API.

Один локальный React-проект, `npm run dev`, без бэкенда (кроме внешнего локального AnythingLLM).

## Стек

- **Vite + React** (JavaScript, без TypeScript — скорость важнее типобезопасности на хакатоне)
- **React Router** — маршруты `/map` (карта+диспетчеризация), `/fuel-report` (топливный отчёт) и `/assistant` (ИИ-чат), общий Layout с навигацией и лого (`ziyrak_ai_logo.svg` как favicon и в шапке)
- **@react-three/fiber + @react-three/drei** — React-обёртка над three.js: декларативные 3D-объекты, `useFrame` для анимации, `OrbitControls`, `Html` для подписей. Без теневых карт (`shadows`/`castShadow`/`receiveShadow`) — на почти вертикальных гранях уступов они регулярно давали артефакты (рваные края, muar), глубина передаётся цветом и светящейся кромкой уступа, а не тенями
- **Tailwind CSS v4** (`@tailwindcss/vite`) — стили панели диспетчера, чата, навигации
- **Zustand** — стор состояния симуляции (машины, точки погрузки, лента событий). Выбран вместо голого useState/Context, чтобы тик раз в 1-2 сек и покадровая анимация машин не вызывали лишние ре-рендеры всего дерева компонентов — подписка на срезы состояния точечная.

## Визуальный стиль сцены

Тёмный "цифровой двойник", по образцу референс-проекта `C:\Users\user\Desktop\ziyrak-ai\ziyrak` (Next.js/R3F, компоненты `components/three/*`) — оттуда взяты конкретные проверенные техники, а не только настроение:

- **Рельеф карьера**: каждый уступ — не полное кольцо, а набор отдельных секторных "кирпичей" (`RingGeometry`/`CylinderGeometry` с `thetaStart/thetaLength`) с небольшим угловым зазором между соседями. Это даёт чёткую раздельность уступов без риска рассинхрона геометрии, который давали вырезанные в стене пандусы (отброшены как источник багов). Цветовой градиент по глубине — холодная сине-стальная палитра (светлый край → тёмное дно), не земляная. У каждого уступа тонкая светящаяся кромка (`meshBasicMaterial` + `AdditiveBlending`, без записи в depth-buffer) — она и держит визуальную "ступенчатость", а не тень.
- **Без теневых карт**: `Canvas` без пропа `shadows`, ни один меш не использует `castShadow`/`receiveShadow`. Причина — не эстетика, а надёжность: тени на почти вертикальных гранях уступов систематически давали артефакты независимо от подбора bias/normalBias. Глубина/объём читаются через цвет + светящуюся кромку.
- **Фон/туман**: тёмно-синий (`#050912`), `fogExp2` той же тональности — вместо неба/заката.
- **Самосвалы**: собранная из примитивов группа (не единый box) — кабина, шасси, приподнятый кузов-самосвал, 4-6 колёс-цилиндров. Подпись-номер над машиной (`Html`), цветовая индикация фазы (базовый цвет / жёлтый пульс + мини-прогрессбар во время погрузки).
- **Точки погрузки**: тонкий столб + светящийся кристалл-маяк на верхушке + светящееся кольцо у основания (`AdditiveBlending`) + плавающая подпись (название + текущая очередь). Цвет кольца отражает загрузку: зелёный (<2), жёлтый (=2), красный (≥3).
- **Дороги**: НЕ вырезаны в рельефе — отдельная светящаяся `TubeGeometry` вдоль кривой (`CatmullRomCurve3`) поверх сцены, полупрозрачная, `AdditiveBlending`, `depthWrite: false`, как в референсе (`HaulRoutes.tsx`). Строится вместе с движением машин (этап 2), не блокирует статичный рельеф.
- **Камера**: `OrbitControls` с удобным дефолтным углом сверху-вбок над карьером.

## Модель данных (симуляция)

```js
LoadPoint {
  id, name, position: [x, z], colorId,
  queueCount            // производное: сколько машин сейчас едут туда/грузятся
}

Truck {
  id, number,
  phase: 'ENTERING' | 'TO_LOAD' | 'LOADING' | 'EXITING' | 'DONE',
  position: [x, y, z],       // текущая интерполированная позиция (для рендера)
  path: [[x,z], ...],        // путевые точки текущего сегмента маршрута
  targetLoadPointId,
  phaseStartedAt, phaseDurationMs,  // для прогресса погрузки и таймингов
  distanceThisShift,          // м, накапливается по мере движения (для отчёта)
  fuelLevel,                   // л, текущий остаток
  fuelConsumedThisShift,       // л, накопленный расход за смену
  fuelBurnRatePerHour,         // л/час — фактическая норма ЭТОЙ машины (обычно = норма автопарка, см. "Аномалии")
  anomalyType,                 // null | 'IDLE_OVERRUN' | 'MECHANICAL_FAULT' — см. "Аномалии"
  anomalyRecommendation,       // строка с рекомендацией диспетчеру, null если аномалии нет
}

DispatchEvent {
  id, ts, truckNumber, fromLabel, toLoadPointId, reason   // человекочитаемая причина
}

TruckSessionRecord {              // сохраняется в sessionLog даже после DONE — основа отчёта
  truckNumber, totalDistance, totalFuelConsumed, normLPerHour, deviationPercent, status  // status: 'active' | 'завершила смену'
}
```

Фиксированные точки: `ENTRY_POINT` (въезд), `EXIT_POINT` (выезд), 5-8 `LoadPoint` на разных уступах воронки.

## Два цикла обновления

1. **Кадровый цикл** (`useFrame`, ~60 fps): плавно двигает `position` каждой машины вдоль `path` (lerp), анимирует прогрессбар/пульсацию во время погрузки. Не пишет в Zustand каждый кадр — использует локальный `ref`/интерполяцию на основе временных меток фазы, чтобы не грузить стор.
2. **Тик диспетчера** (`setInterval`, 1000-2000 мс — имитация прихода данных с трекеров, помечено комментарием `// TODO: заменить на реальные данные трекеров в проде`): проверяет, какие машины завершили текущую фазу (по времени/расстоянию), переводит их в следующую фазу, освобождает машины из очереди точки, вызывает алгоритм диспетчеризации для машин, доехавших до `ENTRY_POINT` или освободившихся после `LOADING`, обновляет `queueCount`, пишет событие в `events`, начисляет расход топлива и пробег (см. "Топливо" ниже) для машин в фазах `TO_LOAD`/`LOADING`, решает про спавн новой машины на въезде (случайная пауза, чтобы всего активных машин было 6-10). При переходе машины в `DONE` — её финальные показатели фиксируются в `sessionLog` (запись остаётся в отчёте, сама машина исчезает со сцены).

## Алгоритм диспетчеризации (`src/simulation/dispatch.js`, чистая функция)

```
для освободившейся машины:
  1. посчитать евклидово расстояние от текущей позиции машины до каждой LoadPoint
  2. исключить точки с queueCount >= 2
  3. если остались точки — выбрать ближайшую
  4. если все перегружены — выбрать точку с минимальным queueCount (при равенстве — ближайшую)
  5. вернуть {targetLoadPointId, reason} — reason описывает, почему выбрана именно эта точка
     (например: "точка A перегружена (3 маш.), точка B ближайшая свободная (420 м)")
```
Решение всегда пишется в `events` независимо от режима.

## Топливо (`src/simulation/fuel.js`, чистые функции, без LLM в расчёте)

- Норма расхода (`fuelBurnRatePerHour`) — одно значение на весь автопарк (модель БелАЗ-75131), запрашивается один раз при загрузке страницы 1 через RAG-запрос к AnythingLLM: *"Какой нормативный расход топлива в час у БелАЗ-75131?"*. Ответ парсится на число (простой regex на "л/ч" или похожее); если парсинг не удался или сервер недоступен — **fallback на захардкоженное 110 л/час** (середина диапазона 100-120), без блокировки старта симуляции.
- Пока машина в фазе `TO_LOAD` или `LOADING`, каждый тик диспетчера начисляет расход: `deltaFuel = fuelBurnRatePerHour * (tickIntervalMs / 3600000)`, прибавляется к `fuelConsumedThisShift`, вычитается из `fuelLevel`. Пробег (`distanceThisShift`) накапливается по фактически пройденному расстоянию за тик (для `TO_LOAD`/`EXITING`).
- Фактический часовой расход на машину считается как `fuelConsumedThisShift / (время в движении, ч)`.
- Отклонение: `((фактический - норма) / норма) * 100` — положительное = перерасход, отрицательное = экономия. Цвет в UI: зелёный `|откл| <= 5%`, жёлтый `5-15%`, красный `> 15%`.
- Это полностью детерминированная арифметика — LLM участвует только в разовом получении нормы (RAG) и в финальной текстовой сводке отчёта, не в самом расчёте.

## Аномалии/неисправности (`src/simulation/anomaly.js`, чистая функция, без LLM в детекции)

Цель — на демо гарантированно показать несколько машин с перерасходом топлива и понятной диспетчеру причиной, а не только сухую цифру отклонения.

**Как создаются аномальные машины**: при спавне новой машины с вероятностью ~25% ей присваивается один из двух типов (примерно 50/50), это не меняет остальную логику диспетчеризации — машина едет по тем же правилам, просто с изменённым таймингом/расходом:

- **`IDLE_OVERRUN` (простой дольше нормы)** — машине выставляется аномально долгая `phaseDurationMs` для фазы `LOADING` (в 3-5 раз больше обычных 5-8 сек). Перерасход возникает естественно, теми же формулами из раздела "Топливо" — машина реально дольше стоит и реально дольше жжёт топливо на холостом ходу, никакого отдельного расчёта не нужно.
- **`MECHANICAL_FAULT` (техническая неисправность)** — машине выставляется персональный `fuelBurnRatePerHour`, повышенный в 1.3-1.6 раза относительно нормы автопарка, при этом все тайминги фаз обычные. Машина едет штатно, но стабильно жжёт больше нормы.

**Детект** (тик диспетчера, применяется ко всем машинам, не только к специально засеянным — это общее правило, а не спецкейс): если `|deviationPercent| > 15%` (порог "красной" зоны из раздела "Топливо"):
- если машина в фазе `LOADING` и фактическая длительность фазы уже превысила ожидаемую более чем в 1.5 раза → `anomalyType = 'IDLE_OVERRUN'`, `anomalyRecommendation`: "Машина №{N} превысила нормативное время стоянки на точке погрузки ({elapsed} с вместо ~{norm} с) — перерасход на холостом ходу. Рекомендация: проверить причину простоя, при повторении — направить на технический осмотр."
- иначе → `anomalyType = 'MECHANICAL_FAULT'`, `anomalyRecommendation`: "Машина №{N} показывает стабильный перерасход топлива ({deviation}%) при штатном режиме движения, простой не выявлен. Рекомендация: направить машину на внеплановый технический осмотр."

**UI**: в списке машин панели диспетчера у аномальных строк — предупреждающий значок и рекомендация (разворачивается по клику), цвет — красный, как и отклонение. Кнопка "Объяснить причину" рядом с рекомендацией — четвёртый сценарий использования LLM (см. "Интеграция AnythingLLM"), не обязательна для понимания рекомендации (текст уже человекочитаем без LLM), но даёт более развёрнутое объяснение при клике.

## Два режима симулятора

- **Random** (по умолчанию): выбор целевой точки — обычный алгоритм; тайминги фаз (время в пути, время погрузки, пауза перед спавном) генерируются со случайным шумом в заданных диапазонах.
- **Scripted**: детерминированный сценарий-демо. На 10-15 секунде работы 2-3 машины подряд принудительно направляются в одну и ту же точку погрузки (в обход обычного отбора, для гарантированной демонстрации затора), точка окрашивается жёлтым/красным по мере роста очереди. Следующая машина после этого проходит через обычный алгоритм и наглядно уходит в другую точку — визуальный кульминационный момент защиты. Переключатель режима — в UI над 3D-сценой.

## Панель диспетчера (сайдбар рядом со сценой)

- Список машин: номер, статус (едет / грузится / простаивает), к какой точке направлена, **плюс топливо**: текущий уровень (л), фактический расход, норма, отклонение % — цветом (зелёный/жёлтый/красный по порогам из раздела "Топливо"); при `anomalyType` — значок ⚠ и рекомендация (см. "Аномалии")
- Список точек погрузки: название, текущая очередь, цветовой индикатор загрузки
- Лента событий диспетчеризации (последние решения, новые сверху)
- Кнопка "Объяснить решение" у последнего события → вызывает LLM (см. ниже), результат показывается прямо в панели под событием; во время ожидания — спиннер/индикатор загрузки

## Страница "Полный отчёт по топливу" (`/fuel-report`)

- Таблица по `sessionLog`: все машины за сессию (активные — с live-обновлением, и завершившие смену — зафиксированные записи). Столбцы: номер, пробег за смену (км — конвертируется из внутренних метров `distanceThisShift` при отображении), общий расход (л), норма (л/ч), отклонение (%), статус.
- Сортировка кликом по заголовку столбца (возрастание/убывание), направление сортировки визуально отмечено (стрелка).
- Кнопка "Сформировать сводку": агрегирует таблицу (сумма/среднее по расходу, список машин с наибольшим перерасходом) в компактный текстовый пакет и отправляет в AnythingLLM с просьбой одним абзацем описать картину для менеджмента. Ответ показывается над/под таблицей. При недоступности ИИ — заглушка, таблица остаётся полностью рабочей и без LLM.

## Интеграция AnythingLLM (`src/lib/anythingllm.js`)

- Единая функция `chatWithWorkspace(slug, message)` → `POST http://localhost:3001/api/v1/workspace/{slug}/chat`, заголовки `Authorization: Bearer ${VITE_ANYTHINGLLM_API_KEY}`, `Content-Type: application/json`, тело `{ message, mode: "chat" }` (уточнить точный формат по офиц. Developer API при реализации, но общая механика запрос/ответ отсюда).
- Env-переменные: `VITE_ANYTHINGLLM_API_KEY` (общий ключ), `VITE_ANYTHINGLLM_WORKSPACE_DOCS` (страница ассистента — чат по документации), `VITE_ANYTHINGLLM_WORKSPACE_DISPATCH` (объяснение решений диспетчера **и** RAG-запрос нормы топлива **и** сводка по отчёту — одно техническое рабочее пространство с техпаспортами); если задан только один slug — используется для всех сценариев.
- Четыре сценария использования, все через одну функцию с разными промптами:
  1. Объяснение решения диспетчера — промпт по шаблону из ТЗ (номер машины, точки A/B, очереди, расстояния).
  2. Разовый RAG-запрос нормы расхода топлива при загрузке страницы 1 (см. раздел "Топливо").
  3. Текстовая сводка по топливному отчёту (агрегаты таблицы → один абзац).
  4. "Объяснить причину" для аномалии — промпт вида: "Объясни диспетчеру простым языком, почему машину {N} рекомендовано направить на технический осмотр. Причина: {IDLE_OVERRUN|MECHANICAL_FAULT}. Отклонение расхода топлива: {X}%, текущая фаза: {phase}, время в фазе: {t} сек (норма ~{norm} сек)."
- Ответ страницы ассистента отображается с источником (документ + страница), если API их возвращает в `sources`/`citations`.
- **Обработка сбоя**: любая сетевая ошибка, таймаут (например, 8 сек) или не-200 ответ — перехватываются, в UI показывается заглушка ("ИИ-сервис недоступен, попробуйте позже" для чата; аналогичный текст в панели диспетчера и в отчёте; для нормы топлива — тихий fallback на захардкоженное значение без сообщения об ошибке, чтобы не мешать демо), без падения приложения.

## Страница "ИИ-ассистент по документации" (`/assistant`)

Простой чат: поле ввода снизу, история сообщений сверху (роль user/assistant), индикатор "печатает…" во время ожидания ответа, отображение источников под ответом ассистента при их наличии.

## Поэтапная сборка

1. Каркас Vite+React+Router+Tailwind+R3F; ступенчатый рельеф карьера, статичные точки погрузки (маркеры-маяки), статичные самосвалы (собранная модель) — тёмный "цифровой двойник" по образцу референс-проекта. **Показать результат.**
2. Движение и конечный автомат фаз (въезд → в пути → погрузка → выезд → завершение), интерполяция, спавн/деспавн с колебанием 6-10 машин, random-режим.
3. Алгоритм диспетчеризации, очереди, цветовая индикация загрузки, scripted-сценарий с затором на 10-15 сек, панель диспетчера с лентой событий.
4. Топливо: начисление расхода/пробега в тике (fallback-норма 110 л/ч), колонки в панели диспетчера, `sessionLog` для уехавших машин, страница "Полный отчёт по топливу" с сортируемой таблицей.
5. Аномалии: засев `IDLE_OVERRUN`/`MECHANICAL_FAULT` при спавне, детект по отклонению в тике, значок и рекомендация в панели диспетчера.
6. Интеграция AnythingLLM: кнопка "Объяснить решение", RAG-запрос нормы топлива при загрузке страницы 1, кнопка "Сформировать сводку" в отчёте, кнопка "Объяснить причину" для аномалий, страница ассистента (чат по документации) — везде graceful fallback при недоступности сервера.
7. Полировка: комментарии `TODO: заменить на реальные данные трекеров в проде` на местах симулятора, финальная проверка навигации и стилей.

## Тестирование / проверка

Формальных unit-тестов не требуется для хакатон-MVP; проверка — визуальная (`npm run dev`) на каждом этапе + ручная проверка алгоритма диспетчеризации, расчёта топлива и детекта аномалий на консольных логах/таблице. Ключевые точки проверки: этап 3 (виден ли затор и переключение на другую точку), этап 4 (сходятся ли цифры отчёта с тем, что видно на сцене), этап 5 (появляются ли за разумное время обе причины аномалии и различаются ли по тексту рекомендации) и этап 6 (не падает ли приложение ни в одном из четырёх LLM-сценариев при недоступном AnythingLLM).
